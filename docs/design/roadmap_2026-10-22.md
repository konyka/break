# Break Runtime Expansion Roadmap

## Purpose

This roadmap decomposes the requested architecture/runtime/editor/operations work into independently reviewable subprojects. It preserves the current C11 engine core, C++11 application/editor layer, Lua scripting choice, existing myui/RHI/platform/task/profiler infrastructure, and the evidence-first documentation policy.

## Ground Rules

- C11 remains the runtime core language; C++11 remains the application/editor layer.
- Lua is the only planned runtime scripting language. Zig is not introduced as a gameplay scripting dependency.
- Main/Game owns mutable World/ECS/script state. Other domains communicate through owned messages, command queues, snapshots, or fences.
- Network callbacks validate/copy/enqueue; they do not call gameplay, ECS, Lua, UI, or RHI.
- Runtime changes require a focused test before implementation and normal/ASan/TSan validation where supported.
- Documentation must distinguish formal runtime targets from focused/test-only targets.
- Runtime Core's global lifecycle is `CREATED -> STARTING -> RUNNING -> QUIESCING -> DRAINING -> STOPPING -> STOPPED/FAILED`; subsystem states are local mappings only, coordinated by one Runtime coordinator.
- Runtime Core formal queues return non-blocking `BREAK_RUNTIME_OVERLOAD` when full; Network/IO/Audio/RHI hot paths never inline. Legacy compatibility behavior, including Task legacy inline fallback, remains separately documented.
- Stage 2 examples use project types `u8/u16/u32/u64/usize` from `engine/src/core/types.h`.
- No subproject may silently claim crash upload, online updates, anti-cheat, distributed World Partition, or production editor integration before its own acceptance tests pass.

## Stage 2 — Runtime design

**Status: design complete; implementation plan is `docs/superpowers/plans/2026-10-22-runtime-core-formalization.md`; design goals only, no runtime implementation claimed.**

Stage 2 统一契约基线：唯一 Runtime coordinator 发布 `CREATED -> STARTING -> RUNNING -> QUIESCING -> DRAINING -> STOPPING -> STOPPED/FAILED`；子系统状态必须标注为局部映射。Runtime Core facade 队列满统一非阻塞返回 `BREAK_RUNTIME_OVERLOAD`，Network/IO/Audio/RHI 热路径禁止 inline；compatibility API 的现有行为与 formal facade 分开记录，legacy Task queue-full inline 保持不变。统一 `BreakRuntimeError` 为 `OK/INVALID/CLOSED/OVERLOAD/OOM/TIMEOUT/STALE/REJECTED/FAILED`；Asset/HotReload 状态方向为 `LOADING/VALIDATING/COMMITTED/FAILED_KEEP_OLD/CANCELLED/TIMEOUT/OOM`，均保持设计目标/未实现。

Outputs:

- `docs/design/runtime_thread_model.md`
- `docs/design/runtime_message_model.md`
- `docs/design/runtime_network.md`

Stage 2 contract addendum: Asset/HotReload formal facades use opaque `u64` request handles with generation, owned `BreakAssetCompletion`/`BreakReloadCompletion`, explicit completion release, request release, and result/state enums for submit, poll, commit, and cancel. The contract is design-only; no source/CMake or Lua VM implementation is implied.

Acceptance:

- Map each proposed domain to existing files and formal CMake targets.
- Define ownership, queue capacity, backpressure, shutdown, and test lanes.
- Define the single Runtime coordinator, global lifecycle, timeout resource retention, and FAILED retry rules; mark subsystem states as local mappings.
- Separate compatibility API behavior from Runtime Core formal facade behavior, including `BREAK_RUNTIME_OVERLOAD`, no hot-path inline, Task legacy inline preservation, and formal task reject/credit policy.
- Distinguish 64 KiB wire fragments, Runtime internal messages, asset manifests/blobs, 16 MiB per-assembly cap, and per-connection aggregate/count budget direction.
- Resolve whether focused ECS/network sources become production libraries before implementation.

## Stage 3 — Lua runtime

**Status: design next; Lua dependency already exists, runtime facade not yet delivered.**

Subprojects:

1. `break_lua_runtime` opaque C11 facade and Lua VM ownership.
2. Module loading, versioned reload, old-version retention on failure.
3. C API bindings for bounded ECS batch commands, configuration, and editor automation.
4. Frame lifecycle and error/stack-budget policy.
5. Optional LuaJIT backend only after the baseline Lua VM contract is stable.

Acceptance:

- Normal/ASan/TSan Lua tests.
- Reload failure preserves the old module.
- Script cannot directly reach raw RHI/physics/network handles.
- Formal production target and documentation.

## Stage 4 — Scene editor

**Status: design next; myui and scene serialization are existing foundations.**

Subprojects:

1. Editor shell and command palette.
2. World outliner/entity inspector.
3. Property editing with undo/redo transactions.
4. Asset browser and reload integration.
5. Viewport/gizmo/scene save-load.
6. Console/profiler/network/render diagnostics panels.
7. Lua console and remote session only after security/transport contracts exist.

Acceptance:

- Editor target is separate from runtime engine.
- Save/load round-trip and undo/redo tests.
- UI thread never directly mutates ECS from another domain.
- Headless/editor smoke lane plus native UI lane where available.

## Stage 5 — Online update, crash reporting, and security

**Status: not implemented; design and threat model required first.**

Subprojects:

1. Signed manifest/content-addressed package format.
2. Chunked download, resume, A/B activation, rollback, and channel policy.
3. Crash context capture, local spool, redaction, upload, symbolization contract.
4. Transport authentication and key/session lifecycle.
5. Replay protection, rate limits, server authority, and client anti-tamper cost model.

Acceptance:

- Cryptographic tests use maintained platform/library primitives; no home-grown authentication.
- Offline update rollback tests and crash-spool recovery tests.
- Security review documents client trust limits and server authority.
- No default remote debug or unsigned update path in release configuration.

## Stage 6 — Graphics API lifecycle

**Status: partially implemented; use existing RHI migration plans.**

Subprojects:

1. Keep Vulkan/D3D12/Metal/headless formal target contracts.
2. Keep OpenGL compatibility target explicitly deprecated.
3. Complete remaining backend capability/FBO/binding gaps through separate plans.
4. Add per-backend native/validation/benchmark evidence.
5. Remove OpenGL only after its documented gate is satisfied.

Acceptance:

- Per-backend compile, headless, native-surface, GPU-runtime, and validation evidence.
- No capability claim without matching runtime evidence.
- Existing RHI plans remain the source of truth for backend-specific work.

- `docs/cross_engine/` Stage 1 is now delivered.

- No complete editor product, crash upload service, online update service, anti-cheat system, or World Partition/Cell streaming runtime is claimed.
